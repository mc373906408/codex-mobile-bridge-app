# Agent Note: 所有已授权电脑共用收件箱，按电脑控制系统提醒

Status: implemented

## Problem

在 A 电脑写草稿时，B 电脑可能已完成任务或正在等用户确认。只看当前电脑的动态会漏掉 B。旧版的云登录默认提醒解决了首次登录没有推送登记的问题。使用多台电脑后，用户还需要让某台安静下来，稍后仍能找到它的事件。冷启动时，持久化的通知点击可能先于账号和电脑目录恢复。

## Decision

收件箱覆盖已保存的直连电脑及当前云账号内经桌面授权的电脑。首页和聊天列表指向同一收件箱。新电脑默认参与。系统提醒的总开关和逐台例外保存在手机的显示偏好中。关掉提醒后，前台仍更新收件箱。已读键包含来源电脑、认证作用域和事件 ID。点开通知时重新核验事件和授权，再切换会话。云账号或目录尚在恢复时先保留点击。

每个来源的一轮轮询只读取一次已认证的 `/api/mobile/events`，Rust 从同一响应产生界面正文和提醒元数据。正文留在前台收件箱内存中，直连系统通知只需要来源和事件类型。各主机独立更新画面，最多四个并发读取。首次读取、作用域切换及解除静音后的首次读取建立静默基线。Android 使用既有前台服务，iOS 直连使用前台本地通知。云端登记按绑定撤销或恢复，已到达的加密事件继续使用原生回执去重。

本决定接管[登录后默认通知](2026-11-05-cloud-notifications-on-login.md)中的开关设计。登录时的默认启用、系统权限及桌面授权继续适用。[手机交付约定](../process/2026-11-05-verified-changes-to-phone.md)持有兼容签名和安装验证要求。

## 桌面交互参照

桌面版本 `af83e8e` 的 `web/shell/app.js` 给最近聊天按置顶、活动时间和会话 ID 排序。项目模式按项目键归组并记住折叠状态。手机把相应排序模式传给网关分页接口，读取原始 `recency`，列表、菜单和写入回执均兼容 `bridgePinned` 与旧 `pinned`。聊天发送方式属于账号和会话的草稿。导航只取消离开时捕获的订阅，迟到的草稿写入不能关闭后来打开的聊天。上下文用量弹窗关闭自己的路由，软键盘打开后附件和引用区域可单独滚动。

## Alternatives considered

- 沿用登录后没有开关的设计，首次使用所需操作最少。多台主机并行工作时，用户只能在系统设置中一起关闭提醒，无法单独静音 B。
- 收件箱和系统通知分别读取现有接口，可以直接复用两个旧调用。新事件可能在两次读取之间到达，而且每台主机会承担两次事件请求。
- 按当前选择的电脑切换监听，连接数最少。用户停留在 A 时，B 的任务请求可能一直等到手动切换电脑。

## Consequences

用户可继续编辑当前聊天，主动点开另一台电脑的事件后可回到原草稿。轮询成本随已授权主机数量增加。离线主机重新连通后，收件箱只能恢复网关仍保留的历史。iOS 后台远程投递需要配置 APNs 的 cloud 构建。已发往 APNs 的提醒与逐台撤销登记之间仍有竞态，普通通知服务扩展只能尽力静默在途提醒，系统通知中心的实际表现需真机验证。

## Testing

Flutter analyze 无问题，完整 Flutter 套件 539 项通过、5 项条件跳过。真实 Rust FFI 回归通过，其中两台独立 HTTP 网关覆盖慢主机不阻塞快主机、每轮只读取一次、主机静音和收件箱作用域；桌面 HTTP 契约、Rust 86 项单测、Android 默认及云推送变体单测、Swift 常规及加密预览测试、桌面 JS 20 项和构建脚本 94 项均通过。iOS 模拟器交互测试验证 A 草稿、B 通知点击、逐台静音和返回收件箱，普通 iOS 模拟器应用覆盖安装并启动成功。

Android ARM64 调试 APK 通过 ELF 与 ZIP 对齐检查，并由 Android debug 证书签名。SHA-256 为 `d4c00a007e576b9bc59763f73b0c8f70786e8d960b3deb0259d3074d17a43351`。测试期间 ADB 未发现 Lenovo L71091 的 USB 或 mDNS 连接，因此没有核对兼容签名、覆盖安装、用户数据保留或真机启动。模拟器交互使用合成事件，不能证明 Android 锁屏行为、厂商后台投递或真实 APNs 投递。iOS cloud 后台通知仍要求配置 APNs 的 cloud 构建；已投递的在途通知与撤销登记之间仍有竞态。
